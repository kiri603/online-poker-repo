# 联网 PVP 实现与后续方案

当前 demo 已接入可运行的 1v1 邀请房间。双方使用同一 Node.js 服务器，分别在西岸、东岸布阵，每方 4,200 预算、最多 100 名，双方准备后统一开战，以全歼、认输或超时掉线结算。沿用 128×84 战场、地形和共享视野。

## 军队模式

所有新部署的军队默认待命。选中部队后可用按钮或快捷键切换，混选时显示“混合状态”。

| 模式 | 行为 |
| --- | --- |
| 待命，C | 不主动移动，只攻击射程内的可见目标，不追击指定目标。 |
| 自动战斗，X | 使用全队共享视野自动寻敌和追击；失去全队视野后停止追踪，不读取敌人的隐藏位置。 |

右键地面是优先执行的手动移动，到达后保留当前模式。战线和推进也属于手动命令。切换模式会清除当前移动、追击和战线指令，立即执行新模式。范围外没有已知敌人时，自动战斗也会停留，需要主动侦察或下达行军命令。单机敌方由独立指挥控制，会主动推进和巡逻，丢失视野后恢复搜索，不使用玩家隐藏坐标；PVP 不启用此人机指挥。

## 如何运行

在 `home-demo` 目录运行：

```powershell
npm run build
npm run dev
```

默认地址为 `http://127.0.0.1:5188`。打开两个独立浏览器页面，一方在主菜单选择“联网对战 → 创建房间”，另一方输入 6 位房间码加入。双方部署后点击“准备”，已准备的一方需先取消准备才能调整军队。联机不能暂停、倍速或中途增援，返回菜单和“认输离开”都会认输。

本次联调服务运行在 `http://127.0.0.1:5189`，避免与机器上原有的 5188 服务冲突。端口可通过 `BATTLE_PORT` 设置。

局域网两台电脑需要使用同一台主机的局域网地址。主机启动示例：

```powershell
$env:BATTLE_HOST = '0.0.0.0'
$env:BATTLE_PORT = '5189'
npm run dev
```

两方都访问 `http://主机的局域网IPv4地址:5189`。若系统防火墙阻止连接，需要主机用户允许此端口的局域网访问。不要让另一台电脑访问自己的 `127.0.0.1`。防火墙无需向公网开放游戏内部端口。生产部署通过 GitHub Actions 在同一域名的 `/war/` 下提供 HTTPS/WSS 服务，详见仓库 `war/deploy/README.md`。

直接打开 `index.html` 可以玩单机；联网入口需要上述服务器。

## 已实现的同步方式

服务器固定 30 Hz 运行战斗逻辑，约 10 Hz 按阵营发送完整快照，浏览器使用 110 ms 位置与朝向插值。浏览器仅提交部署、移动、攻击、模式、战线、推进、准备和认输指令。服务器决定位置、伤害、血量、预算和胜负；联机浏览器不运行战斗模拟。

```mermaid
flowchart LR
  A[西岸浏览器] -->|指令与递增序号| S[Node.js 房间服务器 · 30 Hz]
  B[东岸浏览器] -->|指令与递增序号| S
  S -->|西岸可见快照 · 10 Hz| A
  S -->|东岸可见快照 · 10 Hz| B
```

每个连接由服务器绑定房间席位和阵营。指令序号防止重复执行，回执包含处理结果与拒绝原因；客户端收到回执及相应快照后才确认操作完成。双方准备前不能看到对手的部署。

| 位置 | 职责 |
| --- | --- |
| `server/game-server.js` | HTTP、WebSocket、连接和频率限制、固定逻辑时钟、房间回收。 |
| `server/room.js` | 席位、准备、指令归属、视野过滤、断线和胜负。 |
| `src/game/protocol.js` | 规则版本 `battle-pvp-1`、指令格式校验、64×42 视野掩码。 |
| `src/game/network-client.js` | 创建和加入房间、指令回执、快照、插值、自动重连。 |
| `src/game/simulation.js` | 单机与服务器共用的双方战斗、模式、预算、寻路和结算。 |
| `src/game/battle-controller.js`、`battle-hud.js`、`battle-renderer.js` | 联机操作、模式切换、房间状态、东西岸视角和迷雾显示。 |

## 迷雾与输入校验

每方只收到己方单位和当前可见敌军。敌军移出全队视野后立即从客户端单位列表和插值中移除，不下发其隐藏位置、血量、路径、攻击目标、计划或剩余总人数。己方指定攻击目标隐藏后，快照会清除目标及旧位置字段；模拟本身也停止追踪。

服务器按视野过滤命中、技能、音效和死亡事件。只有起点、终点都可见的弹道才完整下发；不可见的音波终点不会泄露。联网模式关闭 `window.__game` 调试入口。伤害由服务器结算，客户端不通过自己上报血量或命中决定结果。

服务器检查单位归属、有限坐标、兵种、阵型、部署区、预算、人数、计划归属和目标视野。WebSocket 验证同源 Origin，单条消息上限 16 KiB，每连接持续允许 20 条消息/秒、初始突发额度 40 条，并设置连接数、背压、心跳和握手超时限制。HTTP 只提供首页和健康检查，不暴露源码目录。

## 断线与当前边界

断线后服务器继续战斗，保留席位 30 秒，客户端自动尝试重连。恢复时获取全量快照和最后指令序号，丢弃旧插值和过期事件；超过期限判负。准备阶段掉线会取消该方准备。

重连令牌只保存在当前页面内存中，因此仅支持当前页面的短时连接中断。刷新或关闭页面后不能自动恢复席位。房间也只保存在服务端内存中，服务器重启后对局丢失，不提供战绩和排名。

首版没有账号、匹配、排位、观战、旁观加入或重赛房间。当前最大房间数配置是保护性上限，不是经过压测的并发容量。

## 验证结果

- 自动化覆盖默认待命、全队视野追击、失去视野停止、手动接管、双方预算、准备锁定、越权和非法输入、重复指令、迷雾与事件过滤、逐格视野一致、计划回收、短线重连及超时结算。
- 真实 WebSocket 双端验证同 tick 血量一致、全歼结果相反；游戏网络客户端验证等待权威快照、原席位和序号恢复、取消连接。
- 两个独立浏览器上下文验证了东西岸部署、模式按钮与快捷键、统一开战、手动行军和交火、认输结算及页面短线恢复。附加 150 ms 的指令发送延迟后，模式切换与重连仍可完成。
- 1280×720 桌面和 390×844 窄屏检查无横向溢出，状态按钮可操作。真实双机、广域网抖动和多房间并发尚未验证。
- 本机合成场景下，双方各 100 名耄耋向中央行军，90 个逻辑步的平均耗时约 3.6 ms；同时生成并序列化双方快照平均约 19.6 ms、P95 约 24.4 ms，双方快照合计约 68.7 KB。寻路初始化出现约 71 ms 峰值。这是单房间短时测量，不代表持续满负载或公网性能承诺。

## 下一阶段

1. 用真实局域网双机验证断线、不同屏幕和完整对局，再覆盖 100～200 ms 延迟、抖动与丢包环境。
2. 测量满编交战和多房间并发，针对寻路初始化峰值安排计算预算；根据 CPU 与带宽决定每进程房间数，并评估二进制或增量快照。
3. 公网首版采用单台 Node.js 加 HTTPS/WSS 反向代理。暂不需要数据库或 Redis；选定服务器、域名和费用后再部署。
4. 在邀请对局稳定后再增加重赛、账号、匹配与战绩；排位前补齐服务器重启处理、滥用防护和对局记录。
