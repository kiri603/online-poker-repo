## 1. 背景

用户反馈线上游戏经常在游戏过程中突然退出房间，或进入无法操作的状态；当时只有两人游玩。用户暂未记录具体动作、错误提示或故障时间。

排查日期为 2026-10-07，时区为 Asia/Singapore。本次先检查当前仓库实现，并只读访问 README 所列线上首页及其公开前端脚本。首页返回 HTTP 200，当前加载 `/assets/gameSocket-qVwVxJPh.js`。

人数少不能排除网络异常、并发发送竞争和游戏状态挂起。没有故障时段的线上日志、CPU、内存、GC、线程或连接指标，不能确认服务器过载，也不能把本次发现直接认定为那次线上故障的完整根因。

## 2. 更新目标

- 异常断线时保留玩家席位和对局状态，允许在短暂恢复窗口内重新接入。
- 消息发送失败不得中断其他玩家的同步；同一 WebSocket 连接的发送必须串行执行。
- 区分临时服务错误与真实身份失效，避免登录心跳因 HTTP 5xx 将玩家退出游戏。
- 客户端停滞、后台暂停或超时消息未送达时，由服务端按既有超时规则推进对局。
- 旧连接、过期定时器和重复动作不得污染新连接或新的行动阶段。
- 增加针对性回归测试和必要诊断信息，能够区分主动离房、异常断线、身份失效与服务端异常。

## 5. 功能需求

### 5.1 统一消息发送与隔离失败

1. 广播、定向手牌同步、错误响应、强制退出等所有发送路径共用一致的会话发送机制。
2. 同一会话任意时刻只允许一个线程写入消息；可使用现有 Spring WebSocket 能力，不新增依赖。
3. 某一会话关闭或发送失败时，记录必要上下文并处理该会话，继续向其他健康会话发送消息。
4. 禁止把网络发送纳入长时间房间状态锁；必要的发送时间和缓冲区上限应明确且有限。
5. 同一行动导致的事件、手牌和房间快照应保持一致顺序，旧快照不得覆盖新的阶段。需要增加版本字段时，前后端一起检查兼容性。

### 5.2 异常断线恢复

1. 明确区分主动离房、被踢、登出、真实身份失效和异常断线。
2. 主动离房仍及时执行现有退出规则；异常断线不立即因断线判负或清空手牌。
3. 异常断线默认保留 30 秒恢复窗口，作为本次建议值。超期仍未恢复时，执行现有离房及清理逻辑。
4. 前端提示正在恢复连接，保留当前对局显示；恢复完成前不接受会被静默丢弃的游戏操作。
5. 重连采用有界退避，同一时间只保留一个连接尝试。恢复时加入现有房间，不能误走创建房间路径。
6. 同一已认证用户回到原有席位时，恢复其手牌、回合、准备状态、技能状态和挂起选择状态，不因原有昵称已占用而拒绝。
7. 新连接取代旧连接后，旧连接的消息或关闭回调不得清空新连接状态，也不得淘汰玩家。
8. 退出登录、被踢或真实身份失效时停止恢复，继续遵守当前身份校验和账号互斥规则。
9. 旁观者恢复不获得其他玩家私有手牌或技能选择信息。
10. 增加轻量连接活性检测，避免失效连接长期表现为可操作；不得因单次临时延迟立即判负。

### 5.3 登录心跳错误处理

1. HTTP 5xx、网络异常和临时限流等非身份失败不得直接清除登录令牌、关闭游戏连接或退出对局。
2. 真实未认证响应和既有 `FORCE_LOGOUT` 行为仍按现有规则退出，不改变服务端认证授权策略。
3. 心跳不得产生无限重试或重叠请求；暂时无法确认身份时保留状态并按有限策略重试。

### 5.4 服务端超时推进

1. 服务端按既有时间限制和自动处理行为兜底：普通回合 20 秒，借刀相关回合 10 秒，挂起选择或响应 10 秒，选将 20 秒。
2. 覆盖普通出牌、要不起、选将、观星、五谷丰登、固守弃牌、苦肉觉醒弃牌、归心决定和群体锦囊响应等相关路径。
3. 人类客户端不再发送任何消息时，服务端也必须能结束到期阶段。
4. 服务端兜底、客户端自动动作、手动操作和 Bot 动作共用状态校验；同一行动只结算一次。
5. 超时任务执行前校验对应房间、阶段、行动人及截止时间，过期任务不能改变新阶段。
6. 空候选牌或候选牌不足时安全结束或按既有规则降级，不得抛错后永久保持挂起状态。
7. 前端发送失败不得提前将超时标记为已处理；通用错误恢复不得向新的阶段延迟发送旧 `PASS`。

## 6. 非功能需求

- 两人对局即可验证修复，不以增加服务器资源作为完成条件。
- 保持房间级状态变更原子性，发送失败不回滚已经合法完成的游戏动作。
- 连接、超时和离房任务必须有界，并在房间销毁和服务停止时清理。
- 日志记录连接关闭码、消息类型、房间、会话及处理结果，不记录令牌、密码或私有手牌。
- 保持现有牌型、武将技能和锦囊效果，避免顺手重构无关模块。
- 中文文件使用 UTF-8，保留现有文件编码、换行风格和仓库约束。

## 8. 验收标准

1. 双人对局中模拟 WebSocket 异常关闭，30 秒内恢复时玩家席位及手牌仍在，恢复后能继续操作；对手不会立即因该断线获胜。
2. 超过恢复期限、主动离房、被踢和身份失效分别按对应规则结束或清理，不能无限保留幽灵房间。
3. 旧会话关闭时，新会话和对应玩家状态保持有效。
4. 两个线程同时广播、定向同步或返回错误时，同一底层会话不会发生并发写入。
5. 对第一个会话注入发送异常，第二个健康会话仍能收到完整消息。
6. 登录心跳返回 HTTP 503 时保留登录与游戏状态；真实身份失效时仍退出。
7. 模拟页面后台暂停、客户端超时消息丢失或停止发送动作，服务端在对应截止时间后推进游戏。
8. 超时与手动操作竞争时，手牌、弃牌堆、回合索引和技能状态只结算一次。
9. 五谷丰登空候选牌不会导致前端定时器抛错或房间长期挂起。
10. 重连恢复普通回合、选将、观星及其他待响应阶段，显示、手牌与操作状态一致。
11. 旁观者、Bot 和不同玩家的私有状态不混用；不向无权用户同步手牌。
12. 相关测试、后端完整测试及前端构建通过；无法执行的项目在完成报告中明确列出原因。

## 9. 风险与注意事项

- 当前主动退出只调用 `ws.close()`，与异常断线走同一后端入口；修复必须同时处理前后端离房意图。
- 当前 `joinRoom(...)` 拒绝所有已有同名席位，不能只增加前端重连。
- 恢复挂起阶段时，仅广播 `SYNC_STATE` 不足以恢复私有手牌与观星选牌，需要同步相应私有状态。
- 当前房间快照在锁内序列化、锁外广播，并发发送仍有快照乱序风险；仅给底层发送加锁不足以证明完整顺序一致性。
- 服务端兜底会与客户端和 Bot 自动动作重叠，需要复用已有挂起阶段门禁并增加过期任务检查。
- 线上后端运行版本未核实。当前公开前端脚本包含关键缺陷，但不能据此证明线上后端与本地仓库完全一致。
- 已有工作流要求需求确认。任何新增依赖、认证策略或生产操作均需按项目规则另外确认。

## 11. 本次诊断证据

### 11.1 已复现的实现缺陷

修复前只读 Node 内存测试加载当时的 `gameState.js`、`gameSocket.js` 和 `authStore.js`，模拟 Vue ref、浏览器定时器和传输。该诊断阶段没有启动真实游戏服务或创建测试源码。以下行号对应修复前快照。

- 异常关闭码 1006 触发 `gameSocket.js:646` 的 `onclose` 后，游戏和手牌被清空，没有调度重连。
- `gameSocket.js:33` 的 `sendMsg(...)` 在非 OPEN 连接上返回 `undefined`，没有发送消息，也没有错误提示。
- 新连接已 OPEN 时，旧连接的 `onclose` 仍能清空共享游戏状态。
- 五谷丰登处于到期状态而候选牌为空时，`gameSocket.js:160` 抛出 `Cannot read properties of undefined`；超时标记已设置，下一次定时器检查不再发送兜底响应。此项证明空候选状态的处理缺陷，不证明线上当时出现过空候选牌。
- 登录心跳模拟 HTTP 503 时，`authStore.js:349` 把所有非成功响应当作 `UNAUTHORIZED`，清空登录和游戏并关闭连接。

只读 Java JShell 测试提取当前 `GameWebSocketHandler.java:770` 的原广播方法，在内存类中运行，使用本地 Spring WebSocket 7.0.5 依赖和模拟会话。

- 第一名会话发送抛出 `IOException` 后，后续健康会话收到的消息数为 0。
- 两个线程同时调用广播时，同一模拟会话的 `sendMessage(...)` 并发进入数为 2。
- 此项证明原方法不隔离单会话失败且不保护并发发送；模拟会话没有复现真实 Tomcat 写入异常或真实服务器断线。

### 11.2 源码确认的恢复缺口

- `GameWebSocketHandler.java:698` 关闭处理立即调用 `safeLeaveRoom(...)`。
- `GameService.java:1418` 将断线玩家标记为 disconnected，并把 PLAYING 玩家改为 LOST、清空手牌；两人对局可能直接产生胜者。
- `GameService.java:116` 拒绝已有同名玩家或旁观者，没有席位恢复路径。
- 搜索当前后端发现调度仅用于 Bot 动作和表情，没有人类回合、选将或挂起响应的到期兜底。倒计时自动动作由前端定时器发送。
- 广播方法在锁外发送房间快照，当前没有快照版本或统一发送顺序保证。

### 11.3 线上只读核对

- 线上首页及当前游戏脚本均返回 HTTP 200。
- 当前脚本仍包含断线清空游戏、无重连、五谷丰登首张候选牌直接访问，以及非成功登录心跳响应直接退出的逻辑。
- 已读取用户从服务器提供的 `/poker/game.log` 筛选片段，253 行，主要记录时间为 2026-09-20 至 2026-10-05。片段出现 HTTP 响应写入时的 `Connection reset by peer`、无效协议请求与非法路径拦截，未出现可对应本次故障的游戏 WebSocket、并发写入或 OOM 证据。HTTP 连接重置不能单独证明本次游戏故障根因。
- 片段确认服务器登录用户名为 `admin`，但本机现有 SSH 密钥以该用户名登录仍被拒绝。因此未直接读取完整故障时段日志、CPU、内存、GC 或线程指标，未核实线上后端构建版本，未开展真实线上对局和压力测试。

- 所有 WebSocket 发送共用会话级串行发送与失败隔离；快照及提示发送放在房间状态锁外；当前连接在行动锁内再次检查，已排队的旧连接动作不能在新连接接管后执行。
- 服务端按既有期限处理普通回合、借刀、选将、观星、五谷丰登、群体锦囊、固守、苦肉觉醒和归心。空候选池安全结束，过期行动和 Bot 任务不能结算新阶段。
- 登录心跳仅在真实身份失效时清理状态，临时 HTTP 5xx 或网络失败保留登录。补齐 GameBoard 的 onlyHasScrolls 模板绑定，避免只有锦囊时错误禁用要不起。
- 原账号 ID 或原游客 HTTP 会话必须与席位匹配，防止游客昵称重新分配后接管旧席位。既有游客刷新失效、账号互斥、密码与权限规则保持不变。

### 风险与使用说明

- 线上仍运行原代码，需先部署兼容的新后端并重启，再更新前端及刷新页面，避免新前端消息被旧后端拒绝。部署不在本次授权范围。
- 游戏房间仍为内存状态，服务器进程重启不保留对局。30 秒是异常断线恢复期限，超期仍按现有离房规则处理；正常游戏的超时结算在恢复期间继续执行。
- 游客刷新仍按原规则结束该次身份。正式账号在恢复期限内重新加入原房间可恢复原席位，异常网络断线时游客可用原 HTTP 会话自动恢复。
- 验证截图、构建输出、测试日志与依赖 junction 属于本地验证产物，不纳入业务提交。已停止本任务启动的本地验证服务，后续联调需重新启动。

### 规则沉淀与复盘

- 问题现象：两人局也会掉房或停止响应。直接原因包括错误处理把临时失败视为离房、发送异常中断广播，以及只依赖客户端到期动作。
- 深层原因：连接生命周期与游戏生命周期混用，当前会话、行动窗口和私有席位归属缺少一致校验。
- 本次修复和新增验证见上述结果；已在 `AI_CODE_GUIDE.md` 第 9 节记录可复用错误模式，包含 HTTP 错误分类、串行发送、服务端兜底、锁内会话复核、游客席位隔离及模板门禁检查。
